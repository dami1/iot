Do dispositivo único à rede

Até agora cada projeto teve um protagonista: um ESP32, um Arduino, um celular. Um sensor entrava, um som ou uma imagem saía. Mas a sigla IoT — internet das coisas — não é sobre uma coisa conectada. É sobre várias coisas conversando, e o “computador central” deixando de ser o ator principal. Quem usa o sistema raramente vê um computador: vê uma lâmpada que responde, uma planta que avisa que está com sede, uma sala que reage a quem entra.

As duas perguntas da aula
Como as coisas se falam?

Duas perguntas organizam tudo o que vem a seguir. A primeira: como dois ESP32 falam diretamente, sem passar por um roteador nem pela internet? É o território do ESP-NOW. A segunda: como muitos dispositivos falam com o mundo — com um painel, com a nuvem, com a voz? É o território do Node-RED, do Arduino Cloud e da Alexa.

O fio condutor é o mesmo da aula 5, quando os protocolos entraram: cada forma de comunicação resolve um problema e cria outro. Escolher entre elas é uma decisão de projeto, não um detalhe técnico.

  • Local e direto — rápido, sem infraestrutura, mas confinado ao alcance do rádio. (ESP-NOW)
  • Em rede local — vários dispositivos e um painel, tudo dentro do Wi-Fi da sala. (MQTT + Node-RED)
  • Na nuvem — acessível de qualquer lugar, com o preço da dependência de um serviço. (Arduino Cloud, Sinric, Alexa)

ESP-NOW — comunicação direta, sem roteador

O ESP-NOW é um protocolo da própria Espressif (a fabricante do ESP32). Ele usa o rádio Wi-Fi de 2.4 GHz, mas não se conecta a uma rede Wi-Fi: dois ESP32 trocam pacotes diretamente, ponto a ponto, como um mouse sem fio fala com seu receptor. Não há roteador, não há senha de rede, não há internet. E foi exatamente esse o gargalo que apareceu na aula 5 com OSC: a rede da instituição bloqueando o tráfego. O ESP-NOW simplesmente não passa por ela.

Conceito
Pareamento por endereço MAC

Cada dispositivo Wi-Fi tem um endereço MAC — seis bytes únicos gravados de fábrica, algo como 30:C6:F7:23:34:44. No ESP-NOW, um dispositivo envia para outro endereçando o MAC do destino. Descobrir o MAC de cada placa é sempre o primeiro passo. Depois de adicionar o outro como peer, a conexão é persistente: se uma placa reinicia, ela volta a falar com a outra sem novo aperto de mão.

Características que definem o uso

  • Payload de 250 bytes por mensagem (na versão clássica). Suficiente para leituras de sensor e comandos — não para imagem, histórico ou texto longo.
  • Até 20 peers registrados por placa. Dá para montar redes pequenas, não enxames de centenas.
  • Baixa latência e baixo consumo — ideal para controle remoto e sensores a pilha.
  • Alcance de até ~220 m em campo aberto; bem menos entre paredes.
  • Confirmação de envio via callback, mas só no nível do rádio: sabe-se que a placa recebeu, não que ela processou.

Três topologias

O mesmo protocolo cobre arranjos bem diferentes, e o desenho da instalação decide qual usar:

  • Um para um — um controle e um receptor. O caso mais simples.
  • Um para muitos — uma placa envia o mesmo comando para várias. Um controle remoto disparando vários atuadores.
  • Muitos para um — vários sensores enviando para uma placa central. É o padrão gateway, que abre a segunda metade da aula.

Descobrindo o MAC de cada placa

Antes de qualquer envio, rode isto em cada ESP32 e anote o endereço que aparece no monitor serial:

ver código · descobre_mac.ino
#include <WiFi.h>
void setup() {
  Serial.begin(115200);
  WiFi.mode(WIFI_STA);
  Serial.print("MAC desta placa: ");
  Serial.println(WiFi.macAddress());
}

O emissor — enviando uma struct

O jeito limpo de usar os 250 bytes é definir uma struct com tudo que se quer mandar e enviar a struct inteira de uma vez. O __attribute__((packed)) garante que os dados fiquem contíguos, sem espaços de alinhamento.

emissor.ino · envia leitura a cada segundo
#include <esp_now.h>
#include <WiFi.h>

// MAC do receptor (anotado no passo anterior)
uint8_t peerMac[] = {0x30, 0xC6, 0xF7, 0x23, 0x34, 0x44};

typedef struct {
  int sensor;
  float valor;
} __attribute__((packed)) Leitura;

Leitura dados;
esp_now_peer_info_t peer;

// callback: o radio confirmou a entrega?
void aoEnviar(const uint8_t *mac, esp_now_send_status_t status) {
  Serial.println(status == ESP_NOW_SEND_SUCCESS ? "ok" : "falhou");
}

void setup() {
  Serial.begin(115200);
  WiFi.mode(WIFI_STA);
  if (esp_now_init() != ESP_OK) return;
  esp_now_register_send_cb(aoEnviar);
  memcpy(peer.peer_addr, peerMac, 6);
  peer.channel = 0;
  peer.encrypt = false;
  esp_now_add_peer(&peer);
}

void loop() {
  dados.sensor = 1;
  dados.valor = analogRead(34) * 3.3 / 4095.0;
  esp_now_send(peerMac, (uint8_t *) &dados, sizeof(dados));
  delay(1000);
}

O receptor — lendo a mesma struct

O receptor define a mesma struct e registra uma função que roda toda vez que um pacote chega. Não precisa adicionar o emissor como peer só para receber.

ver código · receptor.ino
#include <esp_now.h>
#include <WiFi.h>

typedef struct {
  int sensor;
  float valor;
} __attribute__((packed)) Leitura;

Leitura recebido;

// roda a cada pacote que chega
void aoReceber(const uint8_t *mac, const uint8_t *dados, int tam) {
  memcpy(&recebido, dados, sizeof(recebido));
  Serial.print("sensor ");
  Serial.print(recebido.sensor);
  Serial.print(" = ");
  Serial.println(recebido.valor);
}

void setup() {
  Serial.begin(115200);
  WiFi.mode(WIFI_STA);
  if (esp_now_init() != ESP_OK) return;
  esp_now_register_recv_cb(aoReceber);
}

void loop() {}
Armadilhas que falham em silêncio: um único byte errado no MAC e nada acontece, sem mensagem de erro — confira byte a byte. Se uma das placas estiver também conectada ao Wi-Fi, o ESP-NOW precisa usar o mesmo canal do roteador. E vale lembrar da aula 3: com Wi-Fi ativo, evite os pinos ADC2 para leitura analógica.

O padrão gateway — juntando ESP-NOW e Wi-Fi

Aqui as duas perguntas da aula se encontram. O ESP-NOW é ótimo entre dispositivos, mas não fala com a internet. O Wi-Fi fala com a internet, mas dar conexão Wi-Fi a cada sensorzinho gasta energia e complica o código. A solução elegante combina os dois: vários nós sensores simples conversam por ESP-NOW com uma placa central — o gateway — e só ela carrega a complexidade de falar com a rede.

Arquitetura
Nós simples, gateway esperto

Cada nó sensor só faz uma coisa: ler e enviar por ESP-NOW. Fica barato, a pilha, sem senha de Wi-Fi gravada. O gateway recebe de todos por ESP-NOW e republica para o mundo — por MQTT, que é o protocolo que veremos a seguir. Esse desenho evita dar Wi-Fi a cada sensor e ainda assim torna os dados acessíveis remotamente.

gateway.ino · recebe por ESP-NOW, republica por MQTT (esboço)
// ...includes de esp_now, WiFi e PubSubClient...
void aoReceber(const uint8_t *mac, const uint8_t *dados, int tam) {
  memcpy(&recebido, dados, sizeof(recebido));
  // monta o topico a partir do numero do sensor
  String topico = "casa/sensores/" + String(recebido.sensor);
  mqtt.publish(topico.c_str(), String(recebido.valor).c_str());
}
Por que isto importa para o design: a pessoa que monta a instalação não pensa “ESP-NOW” ou “MQTT”. Ela pensa “tenho cinco sensores espalhados e quero ver tudo num lugar só”. O gateway é a tradução dessa intenção em arquitetura — e é uma decisão que molda custo, autonomia de bateria e alcance do projeto.
Atividade: em trios, montar a topologia muitos-para-um. Dois ESP32 como nós sensores (um potenciômetro cada) e um terceiro como gateway imprimindo no serial o que chega de cada um. Quem é o nó 1, quem é o nó 2? O endereço MAC vira a identidade de cada dispositivo na rede.

Node-RED e as engines de fluxo

O Node-RED é uma ferramenta de programação por fluxo: em vez de escrever código linha a linha, você arrasta blocos (chamados nodes) e os conecta com fios. Cada node faz uma coisa — recebe uma mensagem, transforma, envia adiante. É conceitualmente próximo do Pure Data da primeira aula: o mesmo paradigma de fluxo de dados, só que voltado para serviços web e dispositivos em vez de áudio. Quem entendeu o PD entende o Node-RED rapidamente.

A cola entre tudo
MQTT, o protocolo que faltava

O ESP32 e o Node-RED não se falam direto — eles trocam mensagens por um broker MQTT. O MQTT é leve e funciona por publicação e assinatura: o dispositivo publica num tópico (ex.: casa/sensores/1) e qualquer interessado assina aquele tópico para receber. É o mesmo gancho que deixamos no ar na aula 5, quando o OSC apareceu: o MQTT é a extensão natural daquele fluxo para a internet.

Um fluxo mínimo

  • mqtt in — assina um tópico e injeta cada mensagem no fluxo.
  • function — um pedaço de JavaScript que transforma a mensagem.
  • dashboard — gauges, gráficos e botões para ver e controlar.
  • debug — o equivalente ao monitor serial: mostra o que está passando.

Com vários ESP32, não é preciso um node por sensor: um tópico com curinga, casa/sensores/#, captura todos de uma vez, e uma função roteia pelo nome do tópico. É o lado do gateway que montamos na Parte 1, agora visto de cima.

Local primeiro: um atrativo do Node-RED em 2026 é rodar inteiro na sala — num Raspberry Pi ou num PC — com o broker Mosquitto ao lado. As automações continuam funcionando mesmo se a internet cair, e nenhum dado sai do prédio. Para uma instalação artística num espaço expositivo, essa independência costuma valer mais que o acesso remoto.

Arduino Cloud — o caminho gerenciado

Montar broker, Node-RED e dashboard dá controle total, mas dá trabalho. O Arduino Cloud é o oposto da balança: você declara as variáveis que quer sincronizar, e a placa e o painel passam a refletir os mesmos valores quase sem código de rede. É o mesmo trade-off de sempre — facilidade em troca de limites e de dependência de um serviço.

Como funciona
Variáveis que se sincronizam sozinhas

Você cria uma Thing e define propriedades (ex.: temperatura, luzLigada). O editor gera o esqueleto do código; você só preenche a leitura do sensor. Quando a variável muda na placa, o painel atualiza; quando você mexe num botão do painel, a placa recebe. Suporta ESP32 e ESP8266, atualização de firmware pelo ar (OTA) e dashboards de arrastar e soltar.

Os limites do plano gratuito (importante para a aula): o plano Free permite apenas 2 dispositivos, 25 compilações por dia no editor online e retenção curta de dados — recursos como OTA e API ficam nos planos pagos. Dá para aprender e prototipar; não dá para uma frota. Para a turma, dividir-se em poucos grupos evita esbarrar no limite de compilações no meio do laboratório.

O Arduino Cloud também tem integração oficial com a Alexa — o que nos leva direto ao próximo bloco, onde a voz entra e a mesma tensão entre “local e frágil” e “nuvem e robusto” reaparece.

Alexa — três caminhos, três trade-offs

“Alexa, ligue a luz” parece mágica, mas por baixo há escolhas de arquitetura bem diferentes para fazer um ESP32 obedecer. São três caminhos, e a diferença entre eles é um bom resumo de toda a aula.

CaminhoComo funcionaPreço disso
Emulação local
(Espalexa / FauxmoESP)		O ESP finge ser uma lâmpada Philips Hue ou WeMo; a Alexa o encontra na rede local. Sem conta, sem nuvem.Frágil: Echos novos ignoram a descoberta antiga, roteadores bloqueiam o multicast, e quebra quando a Amazon muda algo.
Nuvem a nuvem
(Sinric Pro)		O ESP abre uma conexão WebSocket segura de saída para o serviço; a skill oficial da Alexa fala com esse serviço.Depende da internet e de um terceiro, mas atravessa firewalls e funciona com todas as gerações de Echo.
Arduino CloudSkill oficial amarrada às Things que você já criou no Arduino Cloud.Simples se você já usa o Arduino Cloud; preso aos limites do plano.
Por que a emulação local é frágil
Um truque de descoberta, não uma API

Bibliotecas como a Espalexa fazem o ESP responder como se fosse uma ponte Hue, usando pacotes UDP de descoberta na rede. Echos de geração mais nova passaram a ignorar esses pacotes, e roteadores frequentemente bloqueiam multicast entre faixas de 2.4 e 5 GHz. A própria documentação da Espalexa avisa que a API usada não é estável e não serve para produção. Ótima para uma demo rápida; arriscada para uma instalação que precisa funcionar no dia.

comparando as duas abordagens · o núcleo de cada uma
// LOCAL - Espalexa: define um dispositivo e um callback
espalexa.addDevice("Luz da sala", luzMudou);
espalexa.begin();
// luzMudou(brilho) e chamado quando a Alexa manda

// NUVEM - Sinric Pro: usa IDs do portal e um WebSocket
SinricProSwitch& sw = SinricPro[SWITCH_ID];
sw.onPowerState(aoLigarDesligar);
SinricPro.begin(APP_KEY, APP_SECRET);
Segurança, de novo: o caminho de nuvem expõe seu dispositivo a um serviço externo — nunca coloque dados sensíveis num broker público de teste, e troque chaves e senhas antes de qualquer instalação que vá ao ar. É a mesma lição do roteador dedicado da aula 5: conveniência e exposição andam juntas.

Backend com p5.js + ESP32 — fechando o arco

O curso começou com o sensor entrando direto no Pure Data. Agora o sensor pode estar em outra sala, falando com a nuvem, e a tela que reage a ele é uma página p5.js no navegador. Falta uma última ponte: o navegador não fala MQTT cru nem UDP, mas fala MQTT por WebSocket. Com a biblioteca mqtt.js, o próprio sketch p5.js assina um tópico e desenha o que chega — sem servidor intermediário.

O fluxo completo
ESP32 → broker → p5.js

O ESP32 publica leituras num tópico do broker. O broker entrega para todos os assinantes. O sketch p5.js, rodando no navegador, é um desses assinantes — conecta por wss:// (WebSocket seguro, compatível com o GitHub Pages) e atualiza o desenho a cada mensagem. É o mesmo papel de ponte do Web Serial da aula 5, agora pela rede em vez do cabo.

sketch.js · o núcleo da conexão (mqtt.js + p5)
let client = mqtt.connect('wss://broker.hivemq.com:8884/mqtt');

client.on('connect', () => client.subscribe('casa/sensores/#'));

client.on('message', (topico, msg) => {
  let valor = parseFloat(msg.toString());
  // guarda o valor para o draw() desenhar
});

A sketch abaixo faz exatamente isso, ao vivo. Para nunca ficar na tela vazia em sala, ela mesma publica leituras simuladas de três “nós ESP32” no broker público e as recebe de volta — você vê os dados saindo para a nuvem e voltando, tudo no navegador. Onde houver um ESP32 real publicando nos mesmos tópicos, ele aparece junto.

ver código · dashboard.js
let nodes = {
  temp: { label: "temperatura", val: 24, target: 24, unit: "C", min: 18, max: 34 },
  umid: { label: "umidade", val: 55, target: 55, unit: "%", min: 30, max: 90 },
  luz:  { label: "luminosidade", val: 500, target: 500, unit: "lux", min: 0, max: 1023 }
};
let conectado = false, log = [], client;
const BASE = "iot-damiao/sala";

function setup() {
  createCanvas(windowWidth, windowHeight);
  conectarBroker();
  setInterval(publicarSimulado, 1500);
}

function conectarBroker() {
  client = mqtt.connect("wss://broker.hivemq.com:8884/mqtt");
  client.on("connect", () => { conectado = true; client.subscribe(BASE + "/#"); });
  client.on("message", (topic, msg) => {
    let k = topic.split("/").pop(), v = parseFloat(msg.toString());
    if (nodes[k] && !isNaN(v)) nodes[k].target = v;
  });
}

function publicarSimulado() {
  for (let k in nodes) {
    let n = nodes[k];
    let passo = (k === "luz") ? random(-80, 80) : random(-1.5, 1.5);
    let novo = constrain(n.target + passo, n.min, n.max);
    if (conectado) client.publish(BASE + "/" + k, novo.toFixed(1));
    else n.target = novo;
  }
}

// draw() desenha uma barra por no, suavizando val ate target
